# 发布与验证

适用范围：10 人以内的邀请制共享厨房，现有 Sites + D1 + R2 架构。

## 每轮开发
1. 从最新主分支创建功能分支，一轮聚焦一个可使用的改进。
2. 运行 `pnpm install --frozen-lockfile`、`pnpm run typecheck`、`pnpm test`、`pnpm run build`。
3. 按 README 初始化本地数据库，再运行 `pnpm run dev`；用本地模拟登录验收。
4. 创建 PR，附 CHANGELOG、本地验证结果及必要截图。另一位维护者体验后合并。

CI 使用 Node 24 和 package.json 中指定的 pnpm。测试使用 Node 内置 SQLite，执行真实历史迁移和业务 SQL；不访问线上数据，也不需要额外测试依赖。

## 发布到现有网站
1. 网站所有者确认 Sites 端没有尚未同步的修改；GitHub 是协作代码来源，合并前比较两端差异。
2. 从已验收的 Git commit 发布到原 Site，保留 `.openai/hosting.json` 的 project_id、D1/R2 绑定和邀请制访问。
3. 如有新增迁移，发布前备份数据并核对迁移；历史迁移不得改写。本轮无新增迁移。
4. 记录 Git commit、Sites 版本、发布时间、操作人及验证结果，确认部署成功后再告知朋友。
5. 验证登录、菜单、已有订单和照片能正常读取；用约定的测试账号验证新增操作，避免随意给真实朋友下单。

无法访问 Sites 项目时，仅交付 GitHub 分支/PR和本地结果；不得声称线上已更新，也不得创建替代站点。

## 回退
- 本轮没有数据库结构变更，可重新发布上一份确认正常的代码；保留所有新产生的订单。
- 后续涉及数据库结构的版本，先检查旧代码兼容性；代码回退不会自动撤销已执行的迁移。
- 数据库与 R2 图片分别备份，定期验证可恢复性；不通过删除线上数据来解决发布问题。

## 本轮验收路径
- 菜单 → 选择菜品 → 昵称/房间号/备注 → 下单 → 我的订单。
- 厨房管理 → 待处理 → 依次接单、制作、完成 → 我的订单确认取餐 → 写评价。
- 我的订单 → 更早的订单 → 返回最新订单。
- 手机宽度下，选择菜品后使用底部「查看点菜单」；检查无横向溢出，操作按钮可点击。
- 网络重试与并发请求由自动化测试覆盖；不要为验证而重复提交真实订单。
